## `finish-breakpoint` — the frame-key result

`fib(6)` traced with a breakpoint on the procedure and one `FinishBreakpoint`
per invocation:

```
invocations observed        25
return values observed      25
out of scope                 0
WRONG RETURN VALUES          0
distinct frame keys         11
distinct call sites          3
stack pointers per site     {main: 1, line-20-left: 5, line-20-right: 5}
```

Sample of `(argument, returned)` pairs, in firing order:

```
(1,1) (0,0) (2,1) (1,1) (3,2) (1,1) (0,0) (2,1) (4,3) (1,1) (0,0) (2,1)
```

**Three distinct call sites, for two source lines.** The two calls in
`fib(n-1) + fib(n-2)` occupy one source line and produce two different return
addresses, exactly as [SPEC-MEM-060](../../docs/MEMORY-MODEL.md#spec-mem-060)
assumed. That assumption is now measured rather than reasoned.

### One interaction worth recording
A `FinishBreakpoint` whose `stop()` returns `True` on a recursive procedure that
also carries an ordinary breakpoint will not fire as expected: the ordinary
breakpoint on the deeper call interleaves first. Returning `False` from `stop()`
gives all 25 correct values. A first attempt at this probe read the failure as
"return values are not observable". They are.

## `only-student-code` — the failure

A plain `step` loop does **not** stay in the student's source. Over 120 steps:

| File entered | Stops |
|---|---|
| `base/runtime/heap_allocator.odin` | 12 |
| `../sysdeps/x86_64/multiarch/memset-vec-unaligned-erms.S` | 12 |
| `base/runtime/internal.odin` | 7 |
| `base/runtime/core_builtin.odin` | 5 |
| `base/runtime/error_checks.odin` | 3 |
| `base/runtime/heap_allocator_unix.odin` | 3 |

**42 of 120 stops, 35%, were outside the student's code**, and one of them was
glibc assembly.

### The mitigation, measured
Check the stopped frame's source file. If it is not the student's, `finish` out
instead of stepping. Same program:

```
student steps recorded         85
finish escapes                  4
cost                         1.31 ms per student step
total                        0.11 s
```

The escape is cheap because `finish` leaves the whole runtime call in one
operation. The confined loop is **not slower per student step** than the naive
one.

## Consequences for the budgets

At 1.31 ms per student step:

| | |
|---|---|
| 300-step exercise | ≈ **0.4 s** |
| 2500-step limit | ≈ **3.3 s** |

Both are far inside [SPEC-PERF-012](../../docs/PERFORMANCE.md#spec-perf-012)
(10 s target) and `wall_ms` (60 s). Compilation, not tracing, is the dominant
cost at this size.

## Incidental observation

At the procedure's declaration line, before the prologue completes, an argument

# Part 2 — second probe pass, same day

Written after the first pass unblocked Phase 1. This pass answered the remaining
measurable questions and **found three things the specification had wrong**.

## Corrections to the specification

### `core:os/os2` does not exist
The package was absorbed into `core:os`. `os.process_start`, `os.pipe`,
`os.read`, and `os.process_wait` are the current names, and
`Process_Desc{command, stdout, stderr, stdin, env, working_dir}` is the current
shape.

Probe: an Odin program launched `gdb --version` through a pipe and read **293
bytes**, exit code 0.

**R-08 closes.** Odin can drive an external process with pipes today. The
correction matters because [ADR-002](../../docs/decisions/ADR-002-implementation-language.md)
named a package that is gone.

### Reading after `free` returns plausible garbage, with no error
```
morto := new(int); morto^ = 5
free(morto)
→ read through the pointer returned 8313165202016105638, no exception
```

The freed region stays mapped. **The tool cannot detect use-after-free by
reading.** The `dangling-pointer` fixture's expected result — `unreadable` — was
wrong for this case.

The `unreadable` path does work, for a genuinely unmapped address:
```
0xdeadbeef → gdb.MemoryError: Cannot access memory at address 0xdeadbeef
```
catchable, and the process survives.

Consequence: two different fixtures are needed, and observing the allocator
(Phase 6) is the **only** mechanism that detects use-after-free. It is no longer
an optimisation of identity; it is the only source of that fact.

### Thread detection by counting is unsound
`thread.create_and_start` followed by a step loop: the thread count at every
stop stayed at **1**, and the program printed from the other thread anyway. GDB
reported `[Thread 0x7ffff7bff6c0 exited]` — the thread lived and died **between
two stops**.

Polling misses it. The event does not:

```
gdb.events.new_thread.connect(handler)   # ignore thread num 1, the main thread
→ recorded steps 6, 7, 8 then stopped at line 8
   line 8 is `t := thread.create_and_start(...)`
```

[ADR-012](../../docs/decisions/ADR-012-single-threaded-target.md) must use the
event hook. A count at each recorded step would have shipped a detector that
never fires.

## Anti-lie observability

Every observation the anti-lie fixtures need is obtainable.

| Fixture | Observation | Result |
|---|---|---|
| `two-empty-slices` | distinguishable? | **Both are `{data: 0x0, len: 0}`.** Identical by content. Only the **variable's own address** separates them. Confirms the identity key must include location, not just contents. |
| `two-equal-lists` | distinguishable? | data `0x7fffffffcd10` vs `0x7fffffffcce0` — distinct |
| `cycle` | self-reference visible? | node `0x5555555b72a8`, `node.prox` = the same address |
| `dynamic-array` | readable? | fields `['data', 'len', 'cap', 'allocator']`, `len=2`, `cap=8`, values `[10, 20]` |
| `corrupt-length` | length readable before use? | `4000000000` read as a plain integer. Nothing stops a naive reader. |
| `prints-utf8` | unit mismatch real? | `"coração ✓"` → **13 bytes, 9 characters** |
| `free-then-allocate` | address reuse observable? | new allocation at `0x5555555b7548` after a free |

## What maps do not give

```
map[string]int → struct map[string]int, fields ['data', 'len', 'allocator']
```

There is **no key or value access through the type**. Reading entries requires
decoding Odin's internal map layout by hand, including the capacity packed into
the low bits of the data pointer.

This was assumed to work in [MEMORY-MODEL.md](../../docs/MEMORY-MODEL.md) §8. It
does not, at least not for free. Tracked as
[R-20](../../docs/RISKS.md#r-20).
